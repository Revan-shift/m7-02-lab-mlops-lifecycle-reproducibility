# ADR 0001: Reproducibility Strategy for NorthStar Models

**Status:** Accepted  
**Date:** 2025-01  
**Authors:** ML Platform team  
**Deciders:** ML Lead, Ops Lead  

---

## Context

NorthStar's ML team currently stores models as unversioned ONNX files in S3
with names like `eta_v2_FINAL.onnx`. There is no experiment tracking, no
dataset versioning, and no record of which code, data, or environment produced
any given file. When a production model behaves unexpectedly, the team cannot
reliably identify what changed or reproduce the run to investigate. Regulatory
pressure from logistics contracts (ISO 27001 audit scope) is increasing, and
at least one client SLA now requires that any model used in routing decisions
can be audited and re-run within 30 days.

---

## Decision

We will enforce reproducibility across four independent layers. Each layer is
owned by the CI/CD pipeline and the model registry; no individual engineer
needs to remember to comply — automation rejects non-compliant runs.

### Layer 1 — Environment

**Tool: Docker + ECR (Elastic Container Registry)**

Every training job runs inside a Docker image whose full `sha256` digest is
recorded in the MLflow run and in the registry `lineage.docker_image_sha`
field. Images are built from a pinned `Dockerfile` in the repository root and
pushed to ECR with both a semantic tag (`eta-trainer:1.4.2`) and its immutable
digest. CI refuses to launch a training job if the image tag resolves to
`latest` or any other mutable reference.

Python dependencies are pinned via `requirements.lock` (generated by
`pip-compile` from `requirements.in`). The lock file is committed to git and
baked into the Docker image at build time. `conda` environments are explicitly
rejected for training jobs (see *Alternatives rejected*).

### Layer 2 — Data

**Tool: Custom hashing script (`scripts/hash_dataset.py`) + S3 versioned bucket**

Before any training job starts, the Airflow DAG runs `hash_dataset.py`, which
computes a SHA-256 digest over the sorted, concatenated bytes of all Parquet
files in the training partition. This `dataset_hash` is:

1. Logged as an MLflow tag on the run.
2. Stored in the registry `lineage.dataset_hash` field (required; run is
   rejected without it).
3. Used as the S3 prefix for a snapshot copy:
   `s3://northstar-data/snapshots/{dataset_hash}/`.

The frozen evaluation split is defined once in `split_manifest.json`
(a JSON file listing file paths and row-range offsets, also SHA-256 hashed
as `split_manifest_hash`). The eval set is **never regenerated** between
training runs; it is committed to git and the hash is pinned in the registry.
This prevents a model from appearing to improve because the eval set drifted.

### Layer 3 — Code

**Tool: Git (GitHub) + MLflow**

The full 40-character `git_sha` of the commit used to launch training is
recorded in every MLflow run and is a required registry lineage field. Mutable
references (branch names, tags) are explicitly rejected by the CI pre-launch
check (`scripts/assert_pinned_sha.sh`). All hyperparameters are logged to
MLflow via `mlflow.log_params()` at the start of training — no hyperparameters
live in the training script itself; they are passed via a `params.yaml` file
that is committed alongside the code and whose path is logged to the run.

Model architecture changes require a git commit (no in-notebook mutation).
Notebooks are banned from the training pipeline; `nbconvert` output is also
not accepted. All training entry points are Python scripts invocable from the
command line with no side effects outside their declared output paths.

### Layer 4 — Randomness

**Convention: Explicit global seed + per-operation seeds**

Every training script accepts a `--seed` argument (default: `42`). The seed is
applied to:

- Python `random.seed(seed)`
- `numpy.random.seed(seed)`
- Framework-specific: `torch.manual_seed(seed)` / `tf.random.set_seed(seed)`
- Data-loader shuffle: `DataLoader(..., worker_init_fn=seed_worker, generator=g)`

The seed value is logged to MLflow as `params.seed` and is a required field in
`params.yaml`. Non-determinism from GPU operations is addressed by setting
`CUBLAS_WORKSPACE_CONFIG=:4096:8` and `torch.use_deterministic_algorithms(True)`
for the ETA model. For the Dispatcher model, where GPU non-determinism is
acceptable given the classification tolerance, the environment variable is set
but `use_deterministic_algorithms` is not enforced — this exception is
documented in `training/dispatcher/README.md`.

## Alternatives Rejected

- **No dataset versioning; rely on S3 object timestamps.**  
  S3 `LastModified` timestamps are set by the upload tool, not by data
  creation time, and are trivially overwritten. A re-upload of different data
  with the same key produces the same timestamp. This gives false confidence
  and has already caused one silent dataset swap in the team's history.

- **Conda environments pinned via `environment.yml`.**  
  `environment.yml` does not pin transitive dependencies unless
  `--no-builds` is used, and build strings are platform-specific. An
  `environment.yml` that installs cleanly on macOS may resolve to different
  package versions on the Linux training runner. Docker with `pip-compile`
  is deterministic across platforms.

- **MLflow autolog only, no explicit `log_params()` calls.**  
  `mlflow.autolog()` captures framework-level parameters but silently omits
  custom preprocessing arguments (e.g., feature normalisation window size,
  city-cluster membership version). Explicit logging is verbose but complete;
  autolog is convenient but lossy.

---

## Consequences

- **Every training job must be launched via the Airflow DAG or the
  `scripts/train.sh` wrapper**, which enforces the lineage field collection.
  Ad-hoc `python train.py` runs are permitted locally for debugging but will
  not produce a registerable model artifact.

- **The team must maintain the S3 snapshot bucket.** At ~500 MB per bi-weekly
  ETA snapshot and ~200 MB per monthly Dispatcher snapshot, storage growth is
  approximately 14 GB/year at current cadence. The 10-version retention policy
  in the registry caps registered model artifacts, but raw snapshots in S3 are
  retained for 30 days beyond the model's archival date (for audit), then
  transitioned to Glacier.

- **Adding a new data source requires updating `hash_dataset.py`** to include
  it in the digest computation. Forgetting this is a failure mode: a new
  feature table not covered by the hash would allow silent data changes.
  A test (`tests/data/test_hash_coverage.py`) enumerates all feature tables in
  the schema and asserts they are present in the hasher's source list.

---

## Revisit If

- The team moves to a managed feature store (e.g., Tecton, Feast on Redis)
  with its own versioning guarantees — at that point `dataset_hash` can be
  replaced by the feature store's native snapshot ID, and `hash_dataset.py`
  can be retired.

- Model count grows beyond ~10 distinct models, at which point per-model
  `params.yaml` management becomes unwieldy and a centralised config service
  (e.g., Hydra + a config registry) should be evaluated.
